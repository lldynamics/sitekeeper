# 工地掌柜数据库迁移方案

当前阶段保留 `sitekeeper.json` 和备份格式，先统一写入通知并将健康扫描移出主线程。下一阶段建议采用 GRDB 与 SQLite，按业务记录增量写入、按项目分页读取。完成存储替换后，还必须移除全量数组和派生索引的常驻依赖，才能降低长期使用时的内存占用。

## Repository 与候选库实现状态

已实现 `Sources/Shared/Services/Repository`，GRDB 固定为 7.11.1，并保留应用的 Package.resolved 以固定解析提交。正式启动和 `DataStorePersistenceActor` 仍使用原 JSON；没有添加自动迁移、双写或切换存储清单的行为。

- `BusinessRepository` 定义按 ID 读取、稳定游标分页、摘要、附件引用、快照导出和带预期 revision 的原子命令批次。项目、财务、附件提供领域查询入口。当前写命令覆盖项目、日志、待办完成状态和财务记录，其他领域写命令将在各自页面接入时补齐。
- `JSONSnapshotRepository` 是隔离快照的兼容适配器，可注入原子持久化闭包；持久化失败不发布内存修改。它不与运行中的 DataStore 同时写正式 JSON。
- `SQLiteBusinessRepository` 仅打开状态为 ready 的候选库。21 个业务集合分别建表，记录正文按行保存 Codable payload；项目、日期文本排序键、标题摘要和金额文本独立成列。关系和附件引用分别建表并设置主外键。共享往来单位的项目查询覆盖主项目和关联项目。历史审计可保留已删除项目的 ID。
- 日志列表以 `(sort_key, id)` 游标翻页，限制 1 至 200 条，不查询正文 payload。游标绑定查询条件和 revision，筛选或数据库版本变化后拒绝继续使用。日期排序键仍保留原文，统一时间语义查询留待页面接入阶段完成。
- 关系使用 `record_keys` 与 `record_links` 的复合外键表达，覆盖项目、财务与票据、图纸与日志/待办/资料、工法关联及文档替换链；它实现了上表所述关联结构，但没有引入所有业务实体的级联删除命令。
- 金额列保持源模型的十进制文本；摘要使用 Decimal，避免 SQL 浮点 SUM。摘要目前是方向金额汇总，不替代首页现有的应收、结算及现金流口径。

`SQLiteCandidateBuilder.build(sourceURL:assetDirectories:)` 是显式候选构建入口。调用方应先结束编辑并等待正式 JSON 保存，随后在维护窗口调用；这个阶段没有将入口接入用户界面。候选目录为源文件旁的 `.sqlite-candidates/<UUID>/`，包含原 JSON、原日期审计副本、SHA-256 清单、附件引用及流式文件哈希、候选 SQLite 和迁移状态。

候选构建在一个 SQL 事务中导入全部记录，逐表保留顺序，验证主键集合、每行正文和索引列、关系、附件引用、记录数量及 SQLite 完整性/外键检查。所有源文件和引用附件在发布前再次校验。已有恢复日志时直接拒绝构建，保留日志交由原恢复流程处理，不在候选构建中改写正式数据。损坏数据、重复或缺失 ID、悬空/跨项目关系、附件缺失、磁盘不足、取消及源数据变化均阻止 ready 发布。

`rollback(candidateDirectory:)` 只废弃候选库并保留全部证据，不用旧 JSON 覆盖任何现存数据。候选库 revision 大于零时拒绝回滚；数据库内状态与外部状态文件共同阻止已打开句柄继续写入已废弃候选。中断或失败后的重试创建新候选，不擅自复用状态不明确的数据库。

验证使用临时合成数据与独立应用标识。测试覆盖 v2/v3、全部 21 个集合、事务内各集合导入故障、提交及发布边界、低磁盘预检、真实 SQLITE_FULL、源文件/附件变化、取消、源文件保全、原子命令失败、乐观并发和回滚。生产规模迁移的内存峰值、真实进程被杀/断电、真实设备压力、所有领域的增量编辑、SQL 聚合优化及正式后端切换仍属于后续验收；目前不宣称正式应用已实现数据库分页或降低了常驻内存。

## 项目与施工日志候选工作区接入

入口：`我的 → 更多设置 → 试用功能 → 项目与日志试用副本`。可从当前已保存数据创建一个新副本，也可继续打开既有 ready 副本。每次创建都生成新的候选目录，不覆盖旧副本。副本编辑不会回写正式 JSON；重新启动后从已有副本入口继续使用。用户确认本轮止于此范围，不进行正式存储切换。

- 创建前等待正常 JSON 保存，并持有现有备份读取租约，阻止清理/恢复破坏迁移读入的附件。源文件变化仍由候选构建器检测并拒绝发布。界面明确提示副本只保留附件引用，不包含附件文件，不是完整备份；本轮只编辑文字和项目基础信息，不增删附件或关联。
- `RepositoryPageModel` 每次保留一页摘要，默认 50 条，翻页替换本页，不累积长正文。上一页保留的只是游标；关闭页面后释放页面模型。SQL 查询不选择 payload，不使用深 OFFSET。项目按开工日期、日志按原业务日期文本排序，可切换新旧顺序，UUID 为同日次级排序键。
- 搜索下推到 SQLite 的 search_text 列，覆盖项目名称/地址/联系人及日志全部文字字段，大小写与重音折叠；百分号和下划线作为普通字符。它是完整文字列上的 contains 查询，尚未采用 FTS，不承诺查询 CPU 与全库大小无关。
- 筛选条件、排序或版本变化会使旧游标失效；旧异步结果不会覆盖新筛选。页间发现并发写入时返回第一页。保存后以及页面重新出现、前台恢复、手动刷新时重新读取；没有跨窗口实时订阅，外部变动可能在下一次刷新前暂时未显示。
- `RepositoryRecordEditor` 只在打开详情时获取单条完整模型与同一读取事务内的 revision。新建/编辑项目和日志通过单个 Repository 命令事务增量写入；事务成功才关闭编辑页、发布刷新信号。失败和版本冲突保留表单内容，用户可明确选择重新载入；不自动覆盖冲突。表单内容仅在当前编辑会话内保留，尚未实现副本专用跨进程草稿。
- 项目编辑覆盖名称、地址、状态、联系人、开工/完工日期；日志编辑覆盖日期、天气、内容、人数、安全、材料、明日计划、质量、整改与确认人。未展示的财务字段、照片引用、工法关联等在整条模型的单行更新中保留。
- `candidate-v2-search` 为既有候选库补建搜索列和 position 索引；升级事务按每批 200 条读取正文并填充搜索列，不改正文、业务版本或原 JSON。增量写入时同步维护搜索列。正式备份 schema 不变。

本轮测试范围包括 JSON/SQLite 查询契约、两种日期顺序、多页稳定去重、1千/1万日志分页、旧候选升级、SQL 读取列与目标行写入证据、旧请求/取消/失败重试、并发编辑冲突、新建后重开、候选目录发现及正式数据隔离，以及实际界面的创建、翻页、搜索、编辑和重启继续使用。结果以本轮验证报告为准。

后续仍需接入原页面的完整筛选/风险摘要、日历与照片墙、附件编辑、删除撤销、跨进程草稿和其他所有领域，再处理备份/Widget/云备份与正式后端切换。生产应用仍有全库 DataStore 数组，创建副本仍需全量解码；当前不能据此宣称正式应用已降低启动或常驻内存。10万记录和真机内存/中断验收尚未覆盖。

## 候选库财务页面（2026-10-24）

入口沿用「我的 → 更多设置 → 项目与日志试用副本」，打开项目后进入「财务记录」。支持按项目、方向、正式/草稿/归档状态、往来单位/票号/备注筛选，以日期和 UUID 稳定分页，每页 50 条；正文与资料关联仅在打开编辑时按 ID 读取。默认查看正式记录。新增与编辑保存单条记录，使用 revision 防止覆盖其他会话的修改；失败保留当前编辑内容，成功后刷新列表和汇总。提醒字段仅保存，不创建系统通知；已有资料关联保留，附件编辑和删除撤销不在本阶段内。

`FinanceRepository.page` 在同一 SQLite 读事务返回当前页和全部匹配记录的金额汇总。汇总沿用正式记录计入、草稿/归档不计入的业务口径，收入减支出不等于现金余额。金额以十进制文本保存，使用 Decimal 流式累加，避免 SQLite 浮点 SUM；不加载完整财务对象数组。缺失金额或精度溢出会明确标识并隐藏合计，原记录仍可查看修正。新写入必须大于零，最多 38 位有效数字；原始输入与模型分离，禁止无效输入静默保存旧值。旧 `summary` 方法保留原 Repository 契约中的全记录方向校验用途，财务 UI 只能使用 `financialPage` 的业务汇总。

候选 schema `candidate-v3-finance` 增加分类、状态、往来单位摘要及筛选索引。打开旧候选时在事务内每批 200 条回填摘要，保留 payload、revision、源 JSON 和旧迁移审计；失败回滚 schema 变更并保留候选文件。原应用 `DataStore` 与 JSON 格式不变，不双写、不切换正式存储。

当前汇总计算随筛选命中条数线性增长，但只流式读取三个元数据列、额外内存有界；搜索仍是归一化文本匹配。已加入 1千/1万财务记录验证，尚未以 10万记录、真机峰值内存或时延门槛验收。后续需要在正式切换前评估事务内维护十进制摘要与更大规模索引策略。迁移/回滚、精确金额、过滤分页、并发快照、增量写入、编辑失败和界面重启隔离的实测结果见本轮验证报告。

## 候选库仓储页面（2026-10-24）

入口：我的 → 更多设置 → 项目与日志试用副本 → 打开项目 → 仓储记录。流水支持每页 50 条、日期顺序、入库/出库筛选，以及材料、规格、单位、往来、经手人与备注搜索。按 ID 打开编辑，新增/修改只写目标流水及必要关系元数据；保留 createdAt 和资料关联，不联动修改材料清单或正式 JSON，不提供附件增删、删除撤销或跨进程未保存草稿。

库存页独立分页，每页最多 50 个材料分组。按项目、材料名称、规格、单位归组，沿用空白压缩和大小写归一，并使用 Unicode 规范形式与结构化分量编码，避免文本分隔符碰撞。不同单位和规格不合并。库存搜索只匹配材料/规格/单位，流水的方向与备注筛选不改变库存；每个分组总是累计完整入出库历史。分组数量、当前页分组和数量合计来自同一数据库读快照。

数量用十进制文本及 Decimal 计算，不通过 Double 或浮点 SQL SUM。保留零库存与负库存，负值明确提示核对。数量缺失、无效或精度溢出的分组不显示误导性库存；缺少名称的旧流水不纳入分组，并显示项目内未纳入条数，原记录仍可修正。新增/编辑数量必须大于零、最多 38 位有效数字；原始输入独立于旧模型规范化属性，保存时回读校验，不会静默保存旧数量。

候选 schema `candidate-v4-warehouse` 新增仓储摘要、分组键、库存搜索列及项目/分组和方向分页索引。旧候选在事务内每批 200 条回填，payload、revision、源 JSON 与审计副本保持不变；异常回滚本次 schema。SQL 只为当前页材料流式读取数量与出入库类型，不加载全量仓储模型或全量库存结果。分组计数和搜索仍随项目记录规模增长；单个材料的汇总成本随该材料流水数增长。尚未引入预计算库存表、10万条验收、真机时延/内存门槛或正式切换。

测试覆盖稳定分页、1千/1万条流水、规格/单位/项目隔离、大小写与 Unicode 归一、分隔符碰撞、负库存/精确小数/缺失数量、旧候选升级及失败回滚、事务失败、并发快照、单条写入、引用保留、重启、搜索与原 JSON 隔离。实际结果以本轮验证报告为准。

## 当前问题与本次边界

- `DataStorePersistenceActor.persist` 在后台 Actor 全量编码元数据；自动保存已有 500ms 防抖及 3 秒最大等待，相同字节可跳过实际写入，但仍支付编码成本。附件原文件通常独立保存，不能把全部照片字节计入日常 JSON 保存成本。
- 子 Store 是业务数据唯一的内存所有者。本次由各业务属性的 `didSet` 通过不可替换的 `DomainStoreMutationSink` 通知同一个保存协调器；视图读取由子 Store 的 Observation 跟踪。直接子 Store 写入也会触发保存。领域方法仍负责业务校验、删除审计和历史保留规则，脚本继续检查调用约定。
- 初次加载、加载失败、快照应用和备份恢复不自动保存中间状态。显式恢复事务继续管理提交与回滚。
- `DataHealthScanWorker` 接收 Sendable 值快照，在独立 Actor 上扫描；主线程只捕获快照并接受当前版本结果。新修改立即使旧扫描失效。取消不保证中断已进入的同步文件系统调用，但结果不会发布，后续请求串行执行。自动扫描结果未变化时不重复发布可观察状态，同时单独更新扫描新鲜度；手动扫描仍发布完成信息。
- 手动修复后的计数等待扫描完成；被新请求取代时不展示旧扫描计算出的修复数。后台扫描仍是全量检查，并未实现增量目录索引。后台期间值快照可能延长旧数组生命周期，不能声称已经解决常驻内存问题。

## 建议架构

界面通过 `ProjectRepository`、`FinanceRepository`、`AttachmentRepository` 读取分页和摘要，并提交明确的业务命令。Repository 共享一个数据库写入协调器。领域 Store 保存当前页面、筛选条件和少量摘要，不再拥有全库数组；`DataStore` 逐步缩为依赖入口和跨领域事务协调器。

建议使用 GRDB 的数据库访问、迁移及查询观察能力，保留现有值模型到数据库记录的显式映射。这个选择主要基于本项目的多表关联、历史导入、恢复审计和可验证事务需求；不代表 SwiftData 无法实现。依赖版本须在实施时固定，并在当前 Swift 工具链、iOS 17 最低系统上验证。[GRDB 官方说明](https://github.com/groue/GRDB.swift/blob/master/README.md)

采用一个 `DatabasePool`，业务命令在单个写事务中完成。WAL 允许读写并行，但同一数据库仍只有一个写者；不能把多个后台 Actor 当作多个并行写事务。记录锁等待、事务耗时、WAL 大小，并限制长读事务。[SQLite WAL](https://www.sqlite.org/wal.html)

## 表与关系

| 数据 | 建议结构 | 删除及保留规则 |
| --- | --- | --- |
| 项目 | `projects`，沿用 UUID 主键 | 删除命令在一个事务内生成审计、撤销数据和关联变更 |
| 日志、待办、进度 | 独立表，项目外键，业务日期及稳定排序键 | 按现有业务语义逐类决定删除、解除关联或限制删除 |
| 材料、报价、人工、财务、仓储 | 各自独立表；常用项目和日期条件有组合索引 | 金额采用确定精度的整数或十进制文本，禁止迁移中改为浮点近似 |
| 往来单位 | `contacts` 与 `contact_projects` 关联表 | 一个往来单位可关联多个项目，不能把共享实体随单个项目级联删除 |
| 文档、照片、随手记及工法附件 | 元数据表与显式关联表；文件继续独立存储 | 多引用文件仅在最后引用解除后进入可恢复清理队列 |
| 模板、材料库、用户偏好 | 独立表或有类型约束的小型偏好记录 | 保留收藏、排序、软删除与恢复语义 |
| 日期溯源、操作审计 | 独立审计表，保留原始文本与来源 | 未知时区不推断；历史记录不随业务行无条件删除 |

每个连接启用并验证外键约束。只有语义明确、非共享的从属记录使用 `ON DELETE CASCADE`；其余关系使用 `SET NULL`、关联表删除或 `RESTRICT`，由命令解释失败。[SQLite 外键](https://www.sqlite.org/foreignkeys.html)

## 查询与内存

2026-10-26 的正式 JSON 路径增加了局部优化：材料、仓储与记账列表每页显示 50 条；加载完整快照时只重建一次工程活动索引；保存按各集合的写入版本复用编码片段，片段缓存最多 32 MiB。备份恢复或重新加载会清空编码缓存，未知来源的预编码恢复数据仍走原事务路径。

这些改动保留现有 JSON 与备份合同。首次加载仍解码并持有完整数组，每次实际保存仍原子写入完整 JSON；修改某集合仍需编码该集合。它们不等于 SQLite 正式切换，也不构成数据库级分页读取、逐行增量写入或真机内存验收。独立的十万条样本用于核对字段完整性与热缓存编码开销，设备端和恢复事务测试另行记录。

1. 先迁移项目列表和日志列表，再迁移财务、仓储及跨项目搜索。每条垂直流程同时完成读查询、写命令、观察更新和测试。
2. 日志使用 `(project_id, business_date, id)` 稳定游标分页，第一页建议 50 条；避免深页 OFFSET。同日记录必须以 UUID 作为次级排序键。重新筛选后废弃旧游标和请求结果。
3. 列表只查询标题、日期、状态和摘要；正文与附件详情按记录 ID 获取。关闭页面释放页面缓存，保留有界最近访问缓存。
4. 首页数量、金额及逾期数据以 SQL 聚合或事务内更新的摘要提供，避免加载所有行再重建 `ProjectActivityIndexBuilder`。
5. 观察具体项目和查询所需表，去重后在主线程发布页面结果。数据库提交成功才确认保存；失败保留编辑草稿并提供重试。
6. 导出使用一致性读快照与有界批处理。旧 JSON 解码本身仍可能要求全量内存，必须单独测量迁移峰值，必要时设计流式导入器；分页不会自动解决首次迁移峰值。

## 旧数据迁移与切换

1. 在无备份恢复、无导出租约、无待提交编辑的维护窗口开始。保留原 JSON、日期审计、恢复日志和附件清单的原字节及 SHA-256；任何保留失败都停止切换。
2. 先运行现有恢复日志恢复，避免从尚未完成的恢复事务导入。使用当前 v2/v3 解码及日期溯源逻辑；不改写未知日期。
3. 在同一应用存储卷创建候选数据库。写入源文件哈希、迁移版本、进度状态；整个导入在事务内执行，或采用带幂等批次标记的可恢复分批导入。数据库未验收前不能作为生产数据源。
4. 对比每类记录数量、UUID 集、关键字段、金额汇总、关系及附件清单；执行 `integrity_check` 和 `foreign_key_check`。发现旧数据悬空引用或重复 ID 时生成报告并阻止切换，不静默删除或修复。
5. 关闭候选连接，完成检查点并确认没有未纳入的 WAL 内容，原子发布版本化存储清单。启动时依据清单和迁移状态选择唯一数据源；不得猜测“哪个文件更新”或在异常时自动建空库。
6. 在首次数据库写入之前，失败可回到原 JSON。数据库已接收新写入后，不可自动退回旧 JSON：应进入恢复模式，保留数据库及其 WAL，通过经过验证的导出或恢复路径降级，避免丢失新记录。
7. 不使用长期 JSON 与 SQLite 双写。迁移原件按明确保留策略保存，备份覆盖验证完成后再提供用户可控清理。

## 备份与外部文件事务

数据库事务无法同时原子提交照片、PDF 和压缩包。`BackupArchiveRestoreJournal` 所承担的跨文件恢复职责仍需保留或由等价机制替代。日期溯源也属于业务兼容需求，不会因为更换数据库自然消失。

旧 v2/v3 备份保持只读导入兼容。新导出继续通过版本化归档契约输出完整元数据与附件；需要新增格式时单独升级归档 schema，明确旧版应用能否读取。云备份上传成功和保留策略维持现有契约。

SQLite 文件级备份使用在线备份 API 或经过验证的一致性快照，不能仅复制正在使用的 `.sqlite` 文件。恢复到暂存数据库并验证，然后通过跨文件恢复日志完成数据库和附件切换。[SQLite 在线备份](https://www.sqlite.org/backup.html)

## 分阶段验收

| 阶段 | 交付与通过条件 |
| --- | --- |
| 当前修复 | 所有业务集合有保存通知；直接写子 Store 后可重新加载；加载与恢复不写中间态；后台扫描、取消、过期结果和手动刷新有回归覆盖 |
| Repository 接口 | 定义按 ID 修改、分页、摘要、事务和错误契约；以 JSON 适配器跑现有行为测试，不声称已改善内存 |
| SQLite 候选库 | v2/v3、损坏 JSON、重复 UUID、悬空关系、低磁盘、迁移各阶段强制中断及重试测试通过；原件哈希不变 |
| 分页与增量写入 | 1千、1万、10万条合成记录测冷启动、首屏、峰值内存、写入延迟和写入量；SQL 跟踪证实单条待办修改只更新目标记录及必要审计 |
| 正式切换 | 全领域读写、全局搜索、删除撤销、导出恢复、Widget 和云备份回归通过；真机低内存和后台中断验收完成 |

性能门槛在实施前固定设备和基线后确定：首屏读取量应随页大小而非全库增长，单条写入不应编码全库，关闭页面后内存应回落至有界缓存水平。数据库迁移完成的判据必须同时包含增量写入与分页读取，不能以“JSON 被装进数据库的一行”作为完成。

### 候选工作区材料清单（2026-10-24）

- 项目页进入材料清单，副本项目首页提供“未关联项目的材料”。按进场日期原文与 UUID 做稳定游标分页（每页 50 条）；支持正反序、采购状态及名称/规格/品牌/供应商/单位搜索。空日期按最早值排序，不推断时区或补写历史日期。
- `materialPage` 在同一读快照返回一页摘要与全部匹配记录的金额。只流式读取数量和单价，使用检查错误的 Decimal 乘法和加法（乘法另以十进制整数系数逐位校验，防止运行库静默舍入或指数下溢错误）；不取完整 payload、不用 SQLite 浮点 SUM。包含所有选中的采购状态，不与财务支出或库存联动。
- 未填单价与数值异常分开计数；完整总额隐藏并展示可计算部分金额。乘法/加法精度不足、溢出或下溢时连部分金额也隐藏。零单价明确表示免费。新增/编辑与原材料录入规则一致，要求名称和单位非空、数量非负（允许零）；单价可留空或为非负数。原始输入独立于模型数字包装器，避免无效编辑保存旧值。
- `putMaterialItem` 复用事务、关联校验与预期 revision，仅更新目标材料记录及其索引。草稿在写入失败和冲突时保留；编辑保留规格、品牌、供应商、采购状态、进场日期和项目归属。
- 候选 schema v5 分批（200 条）回填材料摘要、搜索与日期排序字段并建立采购状态分页索引，不改 payload、原 JSON、附件或业务 revision；升级失败整体回滚。正式存储仍为 JSON，材料删除/撤销、附件生命周期与正式切换不在此阶段。

### 候选工作区报价单（2026-10-24）

- 项目页和“未关联项目的报价”入口读取 `quoteItems`。每页 50 条，按客户确认日期原文与 UUID 稳定分页，支持双序、名称/版本/备注/单位搜索、状态和精确版本筛选。摘要列与覆盖全部匹配记录的金额来自同一读快照，不加载全量 payload。
- 金额沿用现有报表公式：单价 × 数量为基础金额，税额与折扣均基于基础金额，合计 = 基础金额 + 税额 − 折扣。不使用折后计税，不把另存的 contractAmount 加入合计，不自动修改项目合同额或财务记录。所有所选状态/版本都计入，页面明确说明多个版本可同时纳入。
- 历史空税率/空折扣按零读取，超过 100% 的旧折扣按现有报表封顶规则计算，保留原 payload；新建/编辑需名称和单位非空、数量/单价/税率非负（允许零）、折扣率 0–100、合同金额可空或非负。输入草稿独立于数字包装器，失败和冲突保留原始输入；版本、确认日期、备注、合同金额及项目归属随目标行保存。
- Decimal 乘法复用十进制系数校验，百分比换算及加减也检查精度错误；缺失关键数值或精度异常时隐藏全部金额并提示，避免输出部分金额冒充完整总额。不做浮点 SUM 或逐行四舍五入。
- schema v6 在事务内每批 200 条回填报价摘要、搜索、确认日期排序字段，并建立项目/状态/版本分页索引；升级保留 payload、revision、原 JSON、审计和附件，失败整体回滚。目标行使用带 expectedRevision 的增量 UPSERT。
- 正式存储继续使用 JSON。报价批量生成、合同额写回、导出、删除撤销及正式存储切换仍属后续阶段；金额汇总仍需流式扫描全部匹配记录的四个数值字段。

### 候选工作区人工记录（2026-10-25）

- 项目页及“未关联项目的人工记录”入口使用 `laborPage`：每页 50 条，按现有业务日期排序键及 UUID 游标分页，支持正反序、结算状态、工时/工天/待确认单位筛选和班组/工种/备注/日期搜索。详情按 ID 加载，列表不读取完整 payload；页面与全部匹配记录的金额取自同一读快照。
