# Model-aware multi-agent orchestration

Routing baseline reviewed on 2026-10-28 against the current collaboration tool and the [official model guide](https://developers.openai.com/api/docs/guides/latest-model) and [model selection guidance](https://developers.openai.com/api/docs/guides/model-selection). These are starting defaults; repository validation determines whether a result is acceptable.

- The primary agent is the architect, planner, reviewer, and final integrator. Keep complex reasoning, cross-cutting decisions, conflict resolution, and final acceptance in the primary thread.
- The primary agent uses the model and reasoning effort configured for the current chat. These delegation rules do not switch the primary model or establish which model is running.
- Only the primary agent may delegate. Subagents must not spawn additional agents.
- For change, build, or fix requests, inspect the repository first and split suitable work into at most three independent, bounded work packages. Respect the runtime's available concurrency slots. Delegate only when parallel work materially improves speed or quality; complete small or tightly dependent tasks in the primary thread.
- Route delegated work by task shape instead of using one model for every package:
  - Use `explorer` with `gpt-6-luna` at `medium` effort for focused, read-only codebase questions. Use `low` for simple symbol or file lookup; use `gpt-6.1-sol` at `high` when the bounded question requires tracing ambiguous behavior across modules.
  - Use `worker` with `gpt-6-luna` at `medium` effort for routine, low-risk implementation, focused tests with clear expected behavior, and straightforward log analysis. Use `low` only for mechanical edits or extracting known facts.
  - Use `worker` with `gpt-6.1-terra` at `medium` effort for screenshot or UI inspection, bounded presentation fixes, and documentation work based on supplied facts. Use `high` when visual or interaction analysis needs substantial judgment; route complex state, concurrency, or data-flow logic to Sol.
  - Use `worker` with `gpt-6.1-sol` at `high` effort for nontrivial implementation, root-cause debugging, refactoring within an owned module, and judgment-heavy code review. Use `medium` when the approach and contracts are already clear; use `xhigh` for unresolved competing explanations or difficult correctness invariants.
  - Use `worker` with `gpt-6-astra` at `high` effort only for a clearly independent, especially difficult investigation or critical review where the added reasoning is justified. Use `xhigh` for high ambiguity or demanding correctness analysis. Security, data integrity, release decisions, and final acceptance remain with the primary agent.
- Start with the listed effort and adjust using task complexity and observed results. Fix missing context, unavailable tools, or environment failures directly instead of increasing effort. Reserve `max` or `ultra` for exceptional tasks with evidence that lower supported levels are insufficient; never use them as routine defaults.
- Use explicit `explorer` or `worker` settings instead of the legacy `luna_worker` preset, whose fixed model and effort do not match this routing policy. Do not default to older GPT-5.6 models or `gpt-6-sol` when the selected current model is available.
- Before spawning, verify the exact model and effort against the current collaboration tool's supported choices; API documentation does not establish this runtime's availability. If a preferred model is unavailable, use available `gpt-6.1-sol` at `medium` for routine or visual work, or `high` for demanding work (`xhigh` only under the criteria above). Otherwise keep the task in the primary thread. State any substitution and never claim an unsupported configuration ran.
- When selecting any explicit model or effort, use `fork_turns="none"` and pass only the necessary context. Include the relevant repository rules, current dirty-state constraints, and required evidence. With `fork_turns="all"`, omit model and effort overrides because they are inherited.
- Every delegated package must state its goal, selected model and effort, owned files or directories, forbidden scope, dependencies, acceptance criteria, and validation command.
- Never let two write-capable workers own overlapping files. Run dependent packages sequentially. Prefer parallelism for read-heavy exploration, independent modules, focused tests, and log analysis.
- All agents must preserve the dirty worktree and unrelated user changes. Do not commit, push, merge, reset, clean, delete unrelated files, or rewrite history unless the user explicitly authorizes that exact action.
- The primary agent waits for all requested workers, inspects their results and the combined diff, resolves inconsistencies, and runs or assigns one final verification lane before reporting completion.
